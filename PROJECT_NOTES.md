# Project overview — Macro & Travel (Test Shoot Gallery)

Personal static photo gallery for Daniel Marshall's macro/travel photography.
No build system, no framework — plain HTML/CSS/JS generated by Python scripts
that read from the photographer's local Camera Roll.

- **Live site**: https://danielmarshall.github.io/photos/
- **Repo**: https://github.com/DanielMarshall/photos (public, `main` branch)
- **Hosting**: GitHub Pages, "legacy" build type (deploys straight from `main`,
  no Actions workflow). `gh` CLI is already authenticated on this machine as
  `DanielMarshall`.
- **Local project dir**: `C:\Users\dashi\photos` (this repo)
- Site currently labeled "Test Shoot Gallery — not a curated portfolio" — these
  are test/practice shots, not a finished body of work.

## Pipeline (how a new batch of photos gets added)

1. **Find new files**: diff `Camera Roll/exports/` against `manifest.tsv`
   column 2 (`comm -23 <(sort exports-listing) <(sort known-filenames)`).
2. **Generate tiers** with ffmpeg for each new file (see `apply_borders.py`'s
   sibling shell commands in chat history, or re-derive):
   - `images/thumbs/<slug>.jpg` — scale to ≤480px wide, `-q:v 5`
   - `images/medium/<slug>.jpg` — scale to ≤2048px wide, `-q:v 3`
   - `images/full/<slug>.jpg` — plain copy of the source
   - `slug` = lowercased filename, non-alphanumerics collapsed to `-`
     (see `slugify()` pattern used throughout).
   - Append `<slug>\t<original filename>` to `manifest.tsv`.
3. **Strip EXIF from `images/full/*`** with `strip_exif.py` (uses `piexif`,
   `pip install piexif` if missing) — privacy: some personal photos had real
   GPS coordinates embedded, now stripped from every published full-res copy.
   `images/medium` and `images/thumbs` never carry EXIF since ffmpeg's re-encode
   already drops it.
4. **Camera settings for stack composites**: Zerene Stacker PMax/DMap output
   JPEGs have **zero EXIF**. `build_data.py`'s `SOURCE_MAP` dict maps each
   stack composite's filename to a source file that *does* have EXIF (a plain
   single-frame sibling JPG, or an `.ORF` raw via `piexif.load()` — both work).
   Always check for a plain-JPG sibling first (in `exports/` or `Camera Roll`
   root) before falling back to the raw.
5. **Classify + title**: edit `build_data.py`:
   - `classify(original, dt)` — returns `(category, subcategory, location)`.
     Falls through a chain of filename/set membership checks ending in a
     default (currently `"Gladesville", "Garden", "Home"`).
   - `TITLES` dict — `(title, description)` per filename, supplied by the
     photographer. Leave both `""` for photos not yet named (they'll show
     their raw filename in the grid/lightbox instead — this is intentional,
     it's how the photographer identifies untitled photos to describe later).
   - `SORT_OVERRIDE` dict — override the datetime used purely for sort
     position, for the rare shot that should sit next to a *different* day's
     photos of the same subject.
6. **Run `python build_data.py`** — regenerates `images.json` from
   `manifest.tsv` + the dicts above. Prints a category/subcategory count
   summary and flags anything with unresolved settings — should always be 0.
7. **Update `script.js`** if a new category/subcategory was introduced: add it
   to both `SECTION_ORDER` and `SECTION_LABELS` near the top of the IIFE.
8. **Bake borders into the new medium images only**:
   `python apply_borders.py "<original filename 1>" "<original filename 2>" ...`
   — pass the exact `original_filename` values as argv to scope it to just the
   new files (running with **no** argv re-processes *everything*, which would
   double-border already-done images — never do that on an existing site).
   This shells out to `C:\Users\dashi\Claude Local Session\exifborder.py`
   (+ `exifborder.toml` for defaults: dark preset, credit "DANIEL MARSHALL",
   frame count parsed from the description text via regex). Only `images/medium`
   gets borders; `thumbs` and `full` stay clean by design (medium tier doubles
   as a "wallpaper download" — thumbs need to stay clean for the grid, full
   stays clean for pixel-level zoom).
9. **Test locally**: `python -m http.server <port>` from the `photos/`
   directory, open in the Browser pane, sanity-check the new section/photos.
10. **Commit + push**. GitHub Pages rebuilds automatically on push to `main`
    (usually live within ~30-60s; can poll
    `gh api repos/DanielMarshall/photos/pages/builds/latest` if needed).

## Site structure / key files

- `index.html` — shell markup: header, `#sections` (populated by JS),
  video-feature block, footer, lightbox markup, slideshow markup.
- `style.css` — all styling. Dark/light theme via `prefers-color-scheme` +
  `data-theme` override, though this site doesn't currently expose a toggle.
- `script.js` — single IIFE, no dependencies. Renders sections from
  `images.json`, plus the lightbox and slideshow. See "Known gotchas" below
  for two CSS-specificity bugs already fixed here — the pattern is worth
  remembering before adding new `hidden`-attribute elements.
- `images.json` — generated, don't hand-edit (edit `build_data.py`'s dicts
  and regenerate instead, or edits will be lost on the next build).
- `manifest.tsv` — generated append-only log of `slug → original filename`.
  Also don't hand-edit; the shell loop in step 2 above appends to it.
- `build_data.py` — the main data-generation script (categorization, EXIF
  resolution, titles, sort order).
- `apply_borders.py` — border-baking batch script (wraps `exifborder.py`).
- `strip_exif.py` — one-off EXIF-stripping utility.
- `check_settings.py` — quick CLI to dump EXIF settings for one or more
  files in a folder; useful when investigating a new batch.

## The "identify via filename" workflow

Several sections have no `TITLES` entries yet: **Sydney CBD, Chinese Garden of
Friendship, Sydney Town Hall, Queen Victoria Building, Darling Harbour
Piano**. For any photo with no title, the grid shows the raw original filename
as an always-visible caption (monospace, `.filename` class) instead of the
usual hover-only caption, and the lightbox's "File" metadata row also shows
it — both are deliberate, so the photographer can browse the live site and
tell a future session "file X should be called Y, described as Z" without
needing to dig through Camera Roll himself.

## Lightbox/zoom system (script.js)

- Three image tiers: `thumb` (grid), `medium` (default lightbox view, has the
  baked-in border), `full` (zoom target, clean/no border).
- Zoom levels are **Fit / 1:1 / 1:2 / 1:4** — fractions of *native* resolution,
  deliberately capped at 1:1 max (never upscale past real pixels).
- Full-resolution is fetched via streaming `fetch()` with a real
  `Content-Length`-based progress bar (only revealed after a 150ms delay, so
  cached/fast loads never flash it) — the UI only flips into "full-view" mode
  once the blob is fully in hand, specifically to avoid a bug where slow loads
  left zoom controls visible-but-non-functional. The blob URL is cached
  per-photo (instant toggle back and forth) and released on navigating to a
  different photo or closing the lightbox.
- Click-drag a region while at Fit to marquee-zoom into it, with a "spotlight"
  effect (backdrop-filter grayscale + darken) on whatever extra image content
  gets revealed outside the selected region once it's scaled to fill the
  viewport. Current zoom center point is tracked and preserved across zoom
  level changes and panning (mouse drag + arrow keys) so it doesn't recenter
  unexpectedly.
- Medium view hides the whole metadata panel (title/settings/etc.) since
  that's baked into the image's border already; full-res view shows a
  compact 1-2 line summary instead of the old multi-row table.

## Slideshow (script.js)

Fullscreen (Fullscreen API where available), cycles **medium**-resolution
images in the same order as the grid, 10s/slide with a 1.1s crossfade,
preloads every image in the background as soon as it opens. Click/Space to
pause, arrow keys to step, X or Escape to exit.

## Cache-busting

`style.css`, `script.js`, and `images.json` are all loaded with a
`Date.now()` query string (`index.html` injects the CSS/JS tags via a tiny
inline `document.write`; `script.js` appends the timestamp itself when
fetching `images.json`). This means every page load gets the current version
with no hard-refresh needed. **Actual photo image URLs are deliberately NOT
cache-busted** — they're numerous/large and rarely change once published, so
normal browser caching is kept for those.

## Known gotchas (already hit, don't re-discover the hard way)

- **`[hidden]` + a `display` rule with equal specificity**: any element with
  both `hidden` in HTML and a plain `.foo { display: flex/block/... }` rule
  will ignore the `hidden` attribute, because the class selector and the
  `[hidden]` UA-stylesheet rule have equal specificity and the later one in
  cascade order wins. Fixed twice already (`.zoom-bar`, `.lb-loading`) by
  adding an explicit `.foo[hidden] { display: none; }` override. **Any new
  `hidden`-toggled element needs this from the start.**
- **Windows path colons break ffmpeg filtergraph args**: a filter option like
  `result=C:/Users/...` gets mis-parsed because `:` is the filter-option
  separator. Fix: `cd` into the target directory first and use a relative
  filename in the filter string (`result=transforms.trf`), not an absolute
  `C:/...` path.
- **Python/Node called from Git Bash need Windows-style paths**: passing a
  Git-Bash POSIX path (`/c/Users/...`) as a *string argument* (e.g. inside
  `python -c "..."` or a JS `require()`) fails silently/`FileNotFoundError`
  because only the outer shell translates argv paths, not strings embedded
  in another interpreter's code. Use `C:/Users/...` forward-slash paths
  inside such strings instead.
- **Manual CLI overrides to `exifborder.py` skip its camera/lens name
  normalization** (that only runs on its own EXIF-read path). `apply_borders.py`
  replicates the two lookup tables (`CAMERA_NAMES`, `LENS_NAMES`) itself
  before passing `--camera`/`--lens`.
- **GitHub's 100MB hard file size limit** — any video added to the repo needs
  compressing first (scale down + higher CRF). The `video/` folder currently
  has `spider-focus-stack-audio.mp4` (~5MB — 4 baked-in loops of the aligned
  focus-stack burst, ~19.4s, paired with a trimmed/faded Gemini-generated
  music track; poster frame extracted from the actual video content since a
  previous poster mismatch bug showed why that matters) and
  `glitter-oil-focus-attempts.mp4` (~74MB — a 1280-wide cut of the stabilized
  8-minute glitter-oil video, with the photographer's own royalty-free music
  track mixed in, original camera audio removed).

## Video stabilization workflow (ffmpeg vidstab, not part of the site pipeline)

Used once on `C:\Users\dashi\Pictures\Camera Roll\2026_09_13\P9130001.MOV` (a
table-top glitter-oil macro video, table gets bumped/vibrated during
shooting). Two-pass `libvidstab`:

```
ffmpeg -ss 120 -i SRC -vf vidstabdetect=shakiness=8:accuracy=15:mincontrast=0.2:result=transforms.trf -f null -
ffmpeg -ss 120 -i SRC -stream_loop -1 -i MUSIC \
  -vf "vidstabtransform=smoothing=15:input=transforms.trf,unsharp=5:5:0.8:3:3:0.4" \
  -map 0:v:0 -map 1:a:0 -af "afade=t=out:st=<dur-3>:d=3" \
  -c:v libx264 -crf 18 -preset medium -c:a aac -b:a 192k -shortest OUT.mp4
```

`-ss 120` crops the first 2 minutes. `mincontrast` was lowered from the
libvidstab default (0.3) to grab more from the low-contrast/blurry glitter-oil
frames, `shakiness` raised from default (5) to 8. Even so, "too low contrast"
warnings persisted during pass 1 for a handful of frames — **if the camera is
steady and it's the dish/liquid itself moving when the table gets bumped, no
stabilization filter can fix that; it's real subject motion, not sensor
shake.** The photographer confirmed the retried version is "a little less
jerky" and accepted it as-is rather than chasing further tuning.

Current best output: `C:\Users\dashi\Pictures\Camera Roll\2026_09_13\P9130001_stabilized_v2.mp4`
(8:10, 1920x1080@60fps, audio replaced with a licensed-by-the-photographer
track, faded out at the end). A compressed 1280-wide cut of this
(`glitter-oil-focus-attempts.mp4`) was added to the site's `video/` folder,
titled "Focus? what's that again?", placed directly after the Experiments in
Liquids section.
